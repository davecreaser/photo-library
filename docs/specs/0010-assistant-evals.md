# 0010: Assistant access: evals

Status: approved
Issue: #51; epic #55

## Problem

"I change a tool description and have no idea whether Claude got better or worse at using it." Assistant access (specs 0008 and 0009) gives an AI assistant eight tools. Whether it succeeds depends on their descriptions, result shapes and error sentences, and reading them can't tell you whether a change helps. The owner can only try a few requests by hand on their own library. That is slow and not repeatable, and it can't be shared, because the library is private. There is no way to answer "is the new `best_of` description better?" with numbers, or to notice that a change broke something that used to work. Spec 0009's main promise ("it made my photobook": the owner approves the assistant's pick in a minute) has no measure at all.

## User stories

- **US-1** As the owner changing a tool description, I want to run a fixed set of realistic requests against the app and see a pass rate, tool calls and tokens per task, so that I know whether Claude got better or worse at using the tools.
- **US-2** As the owner, I want each run compared with a recorded baseline, with an honest note when a difference is only noise, so that I can tell a real improvement from luck.
- **US-3** As the owner, I want the evals to cover the Best of flow (`best_of`, `propose_selection`, my decision in the window), including how often I would approve the pick unchanged and whether the assistant respects a "no", so that the photobook promise is measured and not just hoped for.
- **US-4** As the owner paying for model calls, I want to see what a run will cost before it starts, a hard cap per task, and a dry run that calls no model, so that an eval never surprises me.
- **US-5** As someone who keeps photos off the cloud, I want the evals to use only generated libraries, never touch any photo folder, never connect to my real library, and never put transcripts in the repo, so that running them is as safe as running the tests.
- **US-6** As the owner, I want to choose the model an eval runs against, so that I can measure the model I actually use with Claude Desktop and Claude Code.
- **US-7** As the owner, when a task fails I want a one-line reason and the transcript on my computer, so that I can see what to change.

## Acceptance criteria

Terms. The **eval** is `scripts/agent-eval/`, run by hand with `node scripts/agent-eval/run.ts` (or `.mjs`, the build decides). A **task** is one request (a prompt), the starting state it needs, an optional **owner action**, and a **grader**. A **run** is one task executed once: a fresh copy of the app data, the built app, one `claude -p` session, grading, clean-up. The **eval library** is the generated photo folder plus a **template** app data folder (scanned, analysed, people and albums seeded), both kept in the **cache** `~/.cache/photo-library-eval/agent/`, outside the repo. A run is **passed**, **failed** (the model's outcome was wrong, or it hit a cap) or **invalid** (the eval itself went wrong: precondition, isolation, crash). Invalid runs are reported but never counted as failures.

- **AC-1 Task set and dry run.** `run --dry-run` prints the ten tasks (id, prompt, owner action, one line on what is graded), the model, runs per task (default 3), the per-run caps and the worst-case cost of the whole eval (AC-9), then exits 0. It launches no app, calls no model and uses no network: it works with the network off and `claude` missing from the PATH. `--task <id>` (repeatable) limits a run or a dry run to those tasks. An unknown id is refused and the valid ids are listed. `--runs N` sets the runs per task (1 to 10).
- **AC-2 The eval library.** One generator (reusing `e2e/library.ts`'s photo and scene helpers) builds a photo folder of generated images. It contains: `trips/norway_2024` (60 photos over 5 days in August 2024: 8 look-alike scenes of 5 shots plus 20 singles); `trips/sintra_2026` (30 photos: 4 look-alike scenes of 5 plus 10 singles); 10 Lisbon photos (May 2026); `trips/poland_2022` and `trips/poland_2024` (12 each); `2024/beach_day` (20) and `2025/beach` (15); 10 red, 10 blue and 10 green 2025 photos, plus 3 red 2024 photos; 320 loose 2024 photos (415 dated 2024 photos in all) and 40 loose 2026 photos (80 in 2026 in all); 10 undated scans; and 10 photos in `private/`, which is ignored by default. The template is made by scanning it in the built app and waiting until content analysis and quality are complete. The eval then seeds the template database, with the app's own `LibraryDb` functions, as the tests do: people "Alex" and "Sam" on fixed photos (8 and 6 of the 2024 beach photos, 6 and 4 of the Sintra photos), 20 favourites, the owner's albums "Sintra 2026" (all 30 Sintra photos) and "Lisbon" (the 10 Lisbon photos), and the assistant album "Beach with Sam" (the 6 Sam photos plus 4 without him). Library and template are cached and rebuilt only when the generator, `SCHEMA_VERSION`, `CONTENT_MODEL_VERSION`, `FACE_MODEL_VERSION` or `QUALITY_VERSION` changes. The build checks its own result: the app's search for "red" in 2025 ranks all 10 red photos above every other photo, and a search for "Iceland" finds nothing. If the content model is missing, or either check fails, it stops with a message saying which, and no run starts.
- **AC-3 The app, headless, per run.** Each run copies the template to a new temp data folder and launches the built app as the e2e tests do: Electron on `out/main/index.js` with `PHOTO_LIBRARY_DATA_DIR` set to the copy, driven by Playwright. It turns assistant access on through the window's own `setAssistantAccess(true)` and writes the returned Claude Desktop setup (`mcpServers` entry: relay command, socket, token) to an MCP config file in the run's temp folder. Before the model is called, a precondition check runs over its own relay connection: `library_overview` must report the expected photo count, albums and people. If it doesn't, the run is invalid. After grading, the app quits and the temp folder is deleted (kept with `--keep`, and its path printed). If `out/main/index.js` is missing, the eval refuses to start and says to run `npm run build`. No app source changes: everything uses the existing preload API, environment variables and relay.
- **AC-4 Claude, headless and isolated.** Each run calls `claude -p "<prompt>"` with `--mcp-config <run file> --strict-mcp-config`, `--output-format stream-json --verbose`, `--model <id>`, the AC-9 caps, `--no-session-persistence`, built-in tools disabled (`--tools ""`), and an empty temp folder as its working directory. Permissions for the eight `mcp__photo-library__*` tools are granted up front, so the model never waits for a prompt. The stream's first (init) event must list exactly the eight Photo Library tools and the one eval MCP server, and nothing else. If it lists any other tool or MCP server (including the owner's own user-scoped `photo-library` server), the run is invalid ("isolation failed: <names>") and the eval stops before any further run. The eval only ever connects to the run's own socket. Any socket or setup outside the run's temp data folder is refused.
- **AC-5 Graded by state, not by words.** After the `claude` process ends, each task's grader reads two things. The first is the proposals' statuses, asked with `proposal_status` over the eval's own connection before the app quits, for every proposal id found in the tool results of the stream. The second is the run's database, opened read-only after the app quits: albums, their photos, `made_by`, and what changed since the template. The model's text is never read for grading. The result is pass or fail, with one plain reason that uses task terms only ("album holds 58 of the 60 Norway photos and 2 others", "made 'Best of 2026' itself"). Graders are tested without any model (`node --test scripts/agent-eval/`): for each task, a hand-built correct state passes, and at least two typical wrong states fail with the expected reason.
- **AC-6 The scripted owner.** For `best-of-approve` and `best-of-reject`, the eval watches the window through Playwright. Within 5 seconds of a proposal appearing (the "Picked by your AI assistant for you to look over" subtitle), it acts as the owner on every proposal in the run: "approve as is" presses Make album without changing anything, and "reject" presses "Back to <album>". Each proposal gets that action once. It never edits a pick. If the `claude` process ends with no proposal shown, the task fails ("no proposal"). The owner script never calls a tool on the model's behalf and never presses anything outside the Best of screen.
- **AC-7 Pick quality, by proxy.** For every proposal in the two Best of tasks, the report gives proxy checks of the pick. All checks pass means the owner **would approve it unchanged (proxy)**. The checks:
  - (a) the count is the one asked for;
  - (b) every photo is from the right album or year;
  - (c) no two photos come from the same generated look-alike scene;
  - (d) Alex and Sam each appear at least once where the source has them.
    The report also gives (e) the overlap with the app's own `best_of` pick for the same album and count, as a Jaccard index (shared photos divided by all photos), for information only. The report gives the would-approve rate per task (for example "would approve unchanged: 2 of 3 proposals"). It always prints this caveat: "Generated photos: this checks the pick keeps the app's rules (no repeats, everyone in it, the size asked for) and follows the app's choice; it can't tell whether you'd like the photos."
- **AC-8 The report.** At the end the eval prints a table and saves it, as Markdown and JSON, in the cache under a timestamped folder. One row per task: passes of valid runs ("2/3"), invalid runs, median tool calls (min to max), median input and output tokens, and median estimated cost. Below the table come the totals (pass rate over all valid runs, total tokens, total estimated cost), the AC-7 would-approve rates, and one line per failed or invalid run: task, run number, reason, and the path of its transcript in the cache. Hitting the turn or cost cap is a fail with the reason "stopped at the cap (30 turns)". A run whose app or `claude` crashed, or that took over 10 minutes, is invalid and the eval moves on to the next run. Ctrl-C quits the app, removes temp folders, prints the partial report, and leaves the photo folder unchanged.
- **AC-9 Cost: shown, capped, estimated.** Tokens per run (input, output, cache read, cache write) and the turn count come from the stream's final result event. The estimated cost uses a price table in `scripts/agent-eval/` (Opus 5.5 $4/$20 per million input/output tokens, Sonnet 5.5 $2/$10, with the published cache read and write multipliers). For a model not in the table, the cost is shown as "unknown", never guessed. The CLI's own cost figure is shown beside the estimate when present. Each run is capped at `--max-turns` (default 30) and `--max-budget-usd` (default $1.00). Before the first run, the eval prints the worst case (runs × per-run budget). Above `--budget` (default $15) it refuses to start unless `--yes` is given.
- **AC-10 Baseline and comparison.** `--save-baseline` writes `scripts/agent-eval/baseline-<model id>.json`, which is committed. It holds only: date, model ID, `claude` CLI version, app commit, a SHA-256 of the `tools/list` result (names, descriptions, schemas), runs per task, and per task the passes, invalid runs, median tool calls, median tokens and median estimated cost. It holds no prompts, transcripts, model text, photo ids or names, and is under 10 KB. When a baseline exists for the model, the report adds per task "baseline 3/3 → now 1/3" and the change in median tool calls and tokens. It flags "tool descriptions changed since the baseline" when the hash differs, and "different CLI version" when that differs. A pass-rate change is marked **likely real** only when the two rates differ by at least half (for example 3/3 → 1/3, or 5/5 → 2/5). Anything smaller is marked **within noise**. The table header says: "3 runs per task: a difference of one run is noise; use --runs 5 or more before deciding." A test checks that a saved baseline has only the allowed keys.
- **AC-11 Safety: no photo folder is ever touched.** The photo folder is fingerprinted with `e2e/library.ts`'s `fingerprint()` before and after every run. On any difference the eval stops at once, prints "The photo folder changed during run N of <task>: stopping", and exits non-zero. The eval writes only in the cache and the system temp folder. It refuses a photo folder that has no eval-library manifest (written by the generator, with the generator version), and a data folder equal to the app's real `userData` path. It never reads or opens the owner's real library or database. No file under `src/` changes, and `test/safety.test.ts` passes unchanged.
- **AC-12 Privacy.** Only the generated eval library is used. People are the placeholders "Alex" and "Sam", and no real name, photo or place is in the generator, tasks or graders. Transcripts, per-run reports and kept temp folders live only in the cache. The only committed outputs are the baseline files (AC-10). The eval sends the prompts and generated-library tool results to the model provider, by hand and only when the owner runs it. The app still opens no port and makes no network call (ADR 0003, ADR 0011). The README section for the eval says all of this, and that the eval must never be pointed at a real library.
- **AC-13 By hand, never in CI.** The eval has no npm script that CI runs, and `.github/workflows/` is unchanged. Its grader tests run with `node --test scripts/agent-eval/`, not under `npm test`. Any extra dependency goes in its own `scripts/agent-eval/package.json`, as `scripts/model-eval/` does, never in the app's dependencies. `npm run typecheck && npm test && npm run e2e` still passes.
- **AC-14 Time and scale.** On the owner's Mac, building the eval library and template takes at most 15 minutes and happens once per cache key (AC-2). A default full eval (10 tasks × 3 runs, sequential) finishes in under 45 minutes, not counting time spent waiting on the model provider's rate limits, which the report states separately. The `whole-year` task's result runs past one search page (over 400 photos against the 200 limit), so paging and `add_to_album`'s 1,000-id limit are exercised. A run started when a cached template from older versions exists rebuilds it first and says so.
- **AC-15 Choosing the model.** `--model <id>` picks the model, with the default from Decision 1 (Open question 1). The exact model ID and `claude` CLI version are printed at the start of the run, and appear in the report and in any baseline saved. A comparison between different models is refused ("baseline is for claude-sonnet-5-5; this run used claude-opus-5-5"), unless `--compare-anyway` is given.

Traceability: US-1 → AC-1, AC-2, AC-3, AC-4, AC-5, AC-8. US-2 → AC-10. US-3 → AC-6, AC-7 (tasks `best-of-approve`, `best-of-reject`). US-4 → AC-1, AC-9. US-5 → AC-4, AC-11, AC-12, AC-13. US-6 → AC-15. US-7 → AC-5, AC-8. Empty case: task `nothing-there`. Error cases: `owners-album` (a refused tool call) and AC-8 (invalid runs, crashes, Ctrl-C). Large case: `whole-year`, AC-14.

## Non-goals

- Running in CI, on a schedule or on every PR.
- Grading what the model says. Pure question tasks ("how many photos of Sam?") are left out, or phrased as album tasks.
- Measuring the owner's real approval rate on their real library. The proxy in AC-7 is all a generated library can give.
- An owner who edits a proposal (swaps, removes) before approving. The script only approves unchanged or rejects.
- Judging pick quality by looking at the photos (a vision model or a person rating them).
- A 100,000-photo eval library. Tool speed at scale is covered by specs 0008 and 0009's own tests.
- Evaluating Claude Desktop, other MCP clients, or several assistants at once.
- Parallel runs. Runs are sequential, because only one proposal shows at a time.
- Any change to the app, its tools or their descriptions. The eval measures them; improving them is later work it informs.
- Windows support for the eval runner (macOS and Linux only; see Product).

## Safety & privacy

- **Photo folder:** the eval reads only its own generated photo folder (through the app, as a user would), and never writes there. The fingerprint is checked before and after every run, and a change stops the eval (AC-11). The app's layered guard is unchanged, and no `src/` file changes. Seeding writes only to the template database in the cache, through `LibraryDb`, as the tests do.
- **Network:** the app is unchanged: no port, no network call (ADR 0003, ADR 0011). The eval itself calls the model provider through `claude`, by hand, like `scripts/model-eval/`'s downloads. What is sent is the prompts and the tool results of a generated library: placeholder names, generated dates, album names from the task setup.
- **The owner's real setup:** the eval never connects to the owner's real app or library. The run's MCP config is the only server loaded (`--strict-mcp-config`), checked from the stream's init event (AC-4). Its own data folder means its own socket and token. The owner's user-scoped `photo-library` entry is never loaded, used or changed.
- **Personal data:** none. Transcripts can contain everything the tools returned, so they stay in the cache, outside the repo. Only the numeric baseline is committed (AC-10, AC-12).

## Product

- **Who it's for:** the owner, and anyone developing the assistant tools. It is a development tool, not a feature of the app, so it has no tier impact and nothing in the app's UI.
- **What it decides:** spec 0009's Product section says the approve rate tells us whether the in-app photobook recipe should copy the assistant flow. Here that rate is a proxy (AC-7). The spec says so instead of claiming more.
- **Owner-specific assumptions:** the tasks are modelled on the owner's own kinds of requests (a trip, a person at a place, the last visit somewhere, a year's photobook), in English. The names, places and folders are placeholders. The runner assumes `claude` (Claude Code CLI, 2.1.x or later) is installed and logged in, plus the app's built output and downloaded models. It is built and tested on macOS (the owner's machine) and should work on Linux. Windows isn't a goal. The owner's library is not used and not measured: nothing here needs it.

## Design

## Open questions

1. **Default model.** The issue recommended the current Sonnet. What is being modelled is the owner's own assistant use, which is Claude Desktop and Claude Code with whatever model the owner picks there. _Recommended: `claude-sonnet-5-5` by default, `--model` for others, and a baseline recorded for each model the owner actually uses (Opus 5.5 too, if that's what you use day to day)._ Sonnet costs half as much ($2/$10 against $4/$20 per million tokens), so it's cheaper to run often. It is also the stricter test of tool descriptions: what Sonnet gets right, Opus usually does too. Haiku 5.5 is left out of the price table until its price is confirmed, so its cost shows as "unknown" (AC-9). Please say which model you use with Photo Library.
2. **Login and isolation: API key or your subscription?** `claude --bare` gives the cleanest isolation (no hooks, plugins or your `~/.claude/CLAUDE.md`), but it needs `ANTHROPIC_API_KEY`, and then the cost is real money. Without `--bare`, the eval runs on your Claude Code login: the cost is notional, but your user CLAUDE.md and settings may still shape the model's behaviour, and that would skew the baseline. _Recommended: use `--bare` when an API key is set, otherwise your login with `--setting-sources` limited as far as the CLI allows; the report and baseline record which, and baselines from the two modes aren't compared._ AC-4's init check blocks other tools and servers either way.
3. **Turn cap flag.** `--max-turns` isn't listed in the installed CLI's help (2.1.322), though `--max-budget-usd` is. _Recommended: the build checks whether `claude -p` accepts `--max-turns`; if not, the eval counts tool calls in the stream and stops the process at the cap._ The behaviour in AC-8 and AC-9 is the same either way.
4. **People are seeded, not recognised.** Generated images have no faces, so "Alex" and "Sam" are written into the template database as confirmed faces, the way the tests do it. _Recommended: yes._ The eval tests tool use, not face recognition. The cost: names come from seeded records, so a bug in face matching wouldn't show here.
5. **Content tasks are about colours.** On generated images, the content model reliably tells only colours apart (as `e2e/library.ts`'s content library already relies on). So `content` asks for "red photos", and "beach" is a folder name match, not what the photos show. _Recommended: accept this._ The cost: a phrase like "the beach" is never tested as a content match. The issue's example "beach photos from 2024 with Person A" is covered as a name match plus a person and a date.
6. **What "would approve unchanged" means.** No generated library can say whether you'd like a pick. _Recommended: the proxy in AC-7 (right size, right source, no two look-alikes, every named person present), with overlap with the app's own pick reported for information but not required._ The assistant may rightly choose differently from the engine, for example when the prompt asks for something. A real approve rate needs your real use, which is Later (local only, with the activity list).
7. **Strictness of graders.** Most tasks require the exact photo set. `content` allows 2 of 10 red photos to be missed, and `owners-album` accepts either no album or a correct new one. _Recommended: as in the table._ Exact sets make a pass meaningful. The tolerance is only where the app's own search, or a reasonable reading of the request, allows a choice. A guess to confirm: that, for "Add the Sintra photos to my Lisbon album", you count doing nothing (and saying why) as correct.
8. **Runs and noise.** 3 runs per task is the smallest useful version and cheap, but a one-run difference means nothing. _Recommended: 3 by default, and `--runs 5` before deciding on a description change; AC-10 marks small changes "within noise"._ A proper significance test isn't worth it at these sizes.
9. **Default caps.** 30 turns and $1.00 per run, and $15 for a whole eval without `--yes`. These are guesses: a typical task should take 5 to 15 tool calls, roughly $0.05 to $0.30 a run on Sonnet. _Recommended: keep these defaults and adjust them after the baseline run shows real numbers._
10. **One baseline per model, committed.** _Recommended: `scripts/agent-eval/baseline-<model>.json`, committed, replaced deliberately with `--save-baseline`._ The alternative, keeping baselines in the cache only, would lose them with the cache and couldn't be shared on a PR that changes a description.
11. **Ten tasks for eight tools.** `library_overview` and `search_photos` are used by every task. `create_album` is used by most, `add_to_album` by `whole-year`, `remove_from_album` by `fix-own-album`, and `best_of`, `propose_selection` and `proposal_status` by the two Best of tasks. `proposal_status` is only used if the model chooses to call it, since the grader asks for itself. _Recommended: accept that coverage; add tasks as the epic grows._
12. **Test-library helpers.** The eval reuses scene and colour helpers from `e2e/library.ts`, which are not all exported today. _Recommended: export them (a test-file change, no app change)._ The alternative is copying them into the eval.
13. **ADR conflicts.** None found. ADR 0003 and ADR 0011 cover the app, which is unchanged. The eval's network use is a developer action on generated data, like `scripts/model-eval/`. CLAUDE.md's "generated photos only" is kept. _Recommended: no new ADR._

## Decisions

- 2026-11-10 (settled in issue #51 and the task, not reopened):
  - An eval set in `scripts/agent-eval/`: about 10 tasks on a generated library; each task runs Claude Code headless (`claude -p --mcp-config …`) against the app's MCP server on a throwaway copy of the app data.
  - Graded by the resulting database state and proposal status, never by what the model says.
  - Reports pass rate, tool calls and tokens per task. Results are cached outside the repo, as for `scripts/model-eval/`.
  - Run by hand, never in CI. Generated photos only, never the owner's library.
  - Smallest useful version: 10 tasks, 3 runs each, a table of pass rates.
- 2026-11-10, the owner's answers: 1. default model `claude-sonnet-5-5`, with `--model` and one baseline per model; 2. `--bare` with `ANTHROPIC_API_KEY` when set, otherwise the owner's login with setting sources limited, the mode recorded and baselines from different modes never compared; 7. `owners-album` passes when the owner's album is unchanged (doing nothing or making an album of its own both pass); all other open questions as recommended (people seeded, colour content tasks, the AC-7 proxy for "would approve unchanged", 3 runs by default and 5 before deciding a description change, 30 turns and $1 per run and $15 per eval, one committed baseline per model, `proposal_status` covered only when the model calls it, scene and colour helpers exported from `e2e/library.ts`, no new ADR). No UI, so no design step.
- 2026-11-10, while building:
  - The tests run with `node --test "scripts/agent-eval/*.test.ts"` (a glob): Node 24 doesn't take a directory argument.
  - Claude Code 2.1.322 has no `--max-turns`, so the runner counts assistant turns in the stream and stops `claude` at the cap (graded as a fail, like the budget cap).
  - Proposals are read from the stream (each `propose_selection` call and its result), then their status asked of the app with `proposal_status` on the eval's own connection.
  - An API error from Claude (a usage limit, an outage) makes the run invalid, not a fail, quoting Claude's message; a usage limit or login error (429, 401, 403) stops the eval, since every later run would fail the same way.
