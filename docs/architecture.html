Architecture walkthrough

How Photo Library organises photos it never touches

Photo Library is a desktop app that turns a folder of camera photos into albums, trips, people and a searchable library. It reads that folder and never writes to it. Everything it learns lives in its own database, and nothing leaves the computer unless the owner turns on assistant access.

The shape of the app

Three processes and a thread, with one folder fenced off

Electron splits the app in two. The renderer is the window: React, sandboxed, with context isolation, so it can only call the 67 functions the preload script exposes as window.api. The main process is Node, and it does the real work: scanning, the database, analysis, search and the assistant server. The heavy content model runs on its own worker thread, because onnxruntime blocks the thread it runs on and the main thread also drives the window.

The one rule

Five layers between the code and the photos

People trust a photo app with their only copy of ten years of photos. So "never write to the photo folder" isn't left to code review: it is enforced in five independent layers, and any one of them would stop a write on its own.

5 · overlapping folders refused
4 · database path asserted writable
3 · safety test audits the source
2 · appFiles is the only writer
1 · fsGuard wraps every fs write
Photo folderevery folder ever chosen stays protected
  1. A guard on the file system itself

    fsGuard.ts is installed first thing at startup. It wraps every Node function that can create, change, move or delete a file, for our code and every dependency. A write must be inside app data or temp and outside every photo folder ever chosen, and the protected rule wins. It fails closed. The content worker thread installs it with no writable folders at all.

  2. One module that writes

    appFiles.ts is the only file allowed to import a write API, and it checks every target again. External tools such as macOS sips only ever get a copy in app temp.

  3. A test that reads the source

    test/safety.test.ts fails if any other file uses child_process, an fs write, trashItem or sharp's .toFile. It then attacks a protected folder with every fs write and delete API, symlinks and letter-case tricks included, and checks the folder is byte-for-byte unchanged.

  4. The database, checked before it opens

    SQLite writes through its own native code, below the guard, so its path is checked with assertWritable before it is opened.

  5. No overlapping folders

    A photo folder that contains, or sits inside, the app data folder is refused. Tests that touch a photo folder snapshot it before and after.

Follow one photo

From a folder on disk to "the best 12 of Sintra"

The clearest way through the code is to follow a single JPEG, from the moment the app finds it to the moment an assistant proposes it for a photobook.

1SCAN

Found and fingerprinted scanner.ts · photoFs.ts

The scanner walks the folder through photoFs, the read-only gateway. Files whose path, size and modified time haven't changed are skipped. Everything else is hashed with SHA-256, a few files at a time so an SSD stays busy without thrashing a spinning disk. Ignored folders (private by default, at any depth) are never read.

incrementalSHA-256 identityJPEG · HEIC · RAW
2ID

A photo is its content, not its path db.ts · ADR 0002

The hash becomes the photo. Where that content lives is a separate row in files, so one photo can have several copies, and moving, renaming or pointing the app at a new folder keeps every album, tag, star and name. A missing file is hidden, not forgotten, until it comes back.

photos 1 — n filescopies shown once
3TIME

When it was really taken metadata.ts · dates.ts · organiser.ts

EXIF gives the recorded time, which has no time zone. Cameras are often wrong: one was a year behind until it was fixed. The organiser compares capture times with dated folder names like 08.25.sail_amsterdam, suggests a correction per camera, and stores it in clock_corrections. The capture time is derived from that, so corrections never stack, and the files are never edited.

taken_at_raw → taken_atEXIF never rewritten
4DECODE

Decoded once, newest first analysis.ts · decode.ts

One background pass reads each photo a single time and feeds every analysis from that decode: 2048 px for faces, 224 px for content, 256 px for quality. HEIC and RAW come from their cached preview. Results are saved per photo as soon as they're done, so quitting loses nothing and a moved file costs nothing.

one read per photoresumableversioned per analysis
5LEARN

Faces, content and quality, all on device faces.ts · contentModel.ts · quality.ts

Faces: YuNet finds each face and five landmarks, the face is aligned to 112×112, and SFace turns it into 128 numbers. Content: SigLIP turns the photo into 768 numbers that live in the same space as a typed phrase, so "snow" can be compared with every photo without reading any of them again. It was chosen by benchmarking six models. Quality: sharpness (Laplacian variance) and exposure, plain arithmetic with no model judging beauty.

YuNet + SFaceSigLIP fp16int8 vectors, 768 B a photomodels SHA-256 pinned
6GROUP

Organised without being asked events.ts · suggestions.ts · faceGroups.ts

A meaningfully named folder is an event. Loose photos split wherever there's an 18-hour gap. Bursts of 20 or more become suggested albums, hidden once you've decided on them or they're mostly in an album already. Faces cluster into people. Grouping errs towards splitting (ADR 0006), because two groups of one person are fixed by typing the same name, while one group mixing two people is a chore to untangle. Name a group once and future photos are recognised.

computed, not storeddecisions kept by photo
7FIND

Search by what's in it photoSearch.ts · vectorStore.ts

"jake beach 2025" is split into a person, a date and a content phrase. Name matches come first, as they always did. Then come content matches: the phrase goes through SigLIP's text encoder and is compared with every photo's vector in SQL with sqlite-vec, filtered by the same dates and people in the same query, and kept above a calibrated minimum score. Only vectorStore.ts knows how vectors are stored, so the index can change without touching search.

exact cosine in SQLmin score 0.0425100k photos tested
8CHOOSE

Best of: the few that tell the story bestOf.ts · bestOfService.ts

Pure functions, so the same album always gives the same pick. Look-alikes (vectors at least 0.93 similar, shot within 10 minutes of each other) collapse to one. The set is cut into moments by time and scene. A greedy pick backed by a max-heap then scores each photo: quality plus your own signals (stars, albums, tags, named people) minus how much it repeats what's already chosen, until every moment and person is covered. Nothing is stored until you make an album from it.

deterministiceveryone includedno near-duplicates
9ASK

Handed to an assistant, decided by you assistantTools.ts · proposals.ts

With assistant access on, Claude can ask for that same Best of and propose a pick. The pick opens in the window for the owner to adjust and keep, or to go back. The assistant learns which by asking the app. It sees ids, dates, album and people's names and the reasons for a pick, and never a path, a place or a pixel.

propose, then approveids, not files

The data model

Everything hangs off the photo, never off the file

One SQLite file in the app's data folder holds the whole library, on Node's built-in node:sqlite with no native module to rebuild for each platform (ADR 0005). The schema is at version 8. Every migration keeps albums, tags, names and settings, and has a test that opens the previous version's database.

Versioned analysis

Each analysis has a version constant (FACE_MODEL_VERSION, CONTENT_MODEL_VERSION, QUALITY_VERSION). Bump one and every photo is analysed again in the background. Search never mixes two models' vectors.

Forgetting is real

Ignoring a folder forgets its photos entirely: faces, vectors, decisions (ADR 0007). Hiding private photos while keeping their analysis wouldn't really keep them private.

Exact keys, exact types

node:sqlite binds JavaScript numbers as REAL, so integer keys such as sqlite-vec rowids are passed as BigInt. A quirk of this kind is written down once in the project's notes so it isn't rediscovered.

Built for agents

An MCP server inside a local-only app

The app makes no network calls, so cloud assistants don't connect to it. Instead it opens a door the owner controls. Off by default, assistant access starts an MCP server on a local socket. Claude launches relay.js, which presents a 32-byte token and then just forwards bytes. Turning the switch off, or "Forget connected assistants", cuts every connection at once. The server is hand-written, with no web framework, so nothing in the app can listen on a port.

Written for a model

Each tool description says when to use it, gives an example call, and explains the album-first route to Best of. Errors name the bad field and what to do next. Results lead with totals, so a model knows when to page.

An allowlist, not a filter

Every result is built field by field from what ADR 0011 allows. A test plants sentinel words in the folder path, folder and file names, camera and hash, and checks that none of them reaches the output of any tool.

The owner stays in charge

An assistant can only change albums it made. Once the owner renames or edits one, it's theirs. Best of picks are proposals: nothing is kept until the owner presses Make album.

Measuring it

Evals that grade what changed, not what the model said

Ten everyday requests run through Claude Code headless against the built app, on a throwaway copy of a generated library of 572 images. Each run is isolated to the eight Photo Library tools. A scripted owner presses Make album or goes back when a proposal appears. Each run is graded on the library afterwards: which albums exist, what's in them, and what happened to each proposal. Caps, a budget gate and a before-and-after fingerprint of the photo folder keep runs cheap and safe.

What it found

The content task failed all 3 runs, the same way each time. Search returned the 10 red photos first, then 4 weaker matches, with only a rank and no strength. Claude kept all 14. This is a gap in the tool, not in the model, and the eval will measure the fix.

Invalid is not a fail

An API error, a usage limit, a timeout or a server that didn't connect makes a run invalid, quoting the reason. Only runs that really reached the model are graded.

Noise, stated

The report says plainly that one run in three is noise. A change counts as likely real only when the pass rate moves by half. Baselines record the model, CLI version, login mode and a hash of the tool descriptions.

How it's built

A spec-first pipeline that agents can run

Features go through the same pipeline, by hand in Claude Code or headless from a GitHub issue. Each stage writes something the next one reads: a spec with testable acceptance criteria, a design, the code, a review, and a QA report that proves each criterion. The owner approves the spec and the design and merges the PR. Agents push feature branches only, and a hook blocks pushes to main, force-pushes and merges.

Docs written for agents

CLAUDE.md holds the hard rules and the gotchas, CONTEXT.md the vocabulary, and each spec a Decisions log. An agent starting cold reads those and knows why things are the way they are.

Lean CI

Linux runs on ready PRs that change code. Windows and macOS run by hand when a change touches paths, sockets or native modules.

Generated photos only

Tests and evals build their own libraries: coloured scenes, bursts, scans and placeholder people. The owner's real photos are never in the repo, the tests or a prompt.
